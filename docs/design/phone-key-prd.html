01

它是什么

一句话：你的手机在身边时，这台 Mac 的锁屏接受一次空密码回车。

要解决的那一刻

安全锁屏设成「立即」之后，去接杯水回来就要重新输一次密码。一天几十次。 于是人把锁屏延迟调长，或者干脆关掉——为了少输密码而削弱了锁屏，这是这个功能真正要避免的事。

明确不做

  • 不做"走近自动打开"。密码框照样出现，你只是不用输字符。走近就开是另一种产品，风险也是另一个量级。
  • 不替代密码。任何状态下 Mac 密码都能登录。这句话在每一屏都常驻。
  • 不做身份识别。它判断的是"配对过的手机在不在附近"，不是"是不是你本人"。
  • 不做远程控制。手机能锁屏，不能开屏（见 §2.4）。
  • 不在手机上编辑快捷键。哪个 App、按哪几个键、每个操作占哪个 cmd 字节， 只能在 Mac 上定——按键录制要一把真键盘，而字节是协议的一部分。 手机上能改的只有看到哪些、什么顺序（§6.5），那是显示偏好，不是配置。
02

安全模型

这一节写在界面之前，因为界面上的每一句话都要对得起它。

2.1 它挡得住什么

  • 冒充你的手机。信标里带的是一个每 30 秒滚动的 HMAC，只有持配对密钥的设备算得出来。 拿一份本仓库的 App 走过去是不行的——那正是 E13 修掉的漏洞。
  • 配对时的中间人。两端各显示六位数字，由人比对。数字来自整场交换的记录， 中间人必须跑两场，两边必然不同。
  • 重放一条指令。手机→Mac 的指令带持久化序号，Mac 只接受严格更大的。
  • 篡改指令。指令字段在 HMAC 覆盖范围内，改一个字节标签就失效。

2.2 它挡不住什么

中继攻击。两个串通的无线电可以把你手机当下的真信标转发到 Mac 旁边。 信标是真的、时间是对的，Mac 无从分辨。

手机被拿走且处于解锁状态。带着它靠近就能进。

这台 Mac 上比手机更值钱的东西。那就老实输密码，或者把这个功能关掉。

2.3 为什么配对必须两边都点

人是两台设备之间唯一一条中间人伪造不了的通道。任何「对方已确认」的消息都要走无线， 而中间人同时握着和两端的不同密钥，可以把它拆开、重新封好再转发。 所以每台设备都必须独立地从人那里收到那声"一样"——蓝牙自己的 Numeric Comparison 也是这个道理。

但这不意味着要你盯两块屏：Mac 点完之后会等着听到手机用新钥匙签名的信标， 听到才说完成。那是事实，不是转述。

2.4 为什么手机能锁屏、不能开屏

system.login.screensaver 这条授权规则是被登录尝试触发的： 有人在锁屏上按了回车，系统才会去问我们的插件。 没有登录尝试，插件根本不运行；而合成事件到不了 SecurityAgent 的会话，root 也不行。

所以手机最多只能预先放行下一次回车，不能代替你按。 曾经有一个「允许下一次解锁」按钮——手机在附近时 Mac 本来就在持续放行，那个按钮 按下去屏幕上什么都不会变，所以它被删了。

03

怎么搭起来的

3.1 谁持密钥，谁碰无线电

配对密钥是 root:wheel 0600——谁能读它，谁就能伪造信标解锁这台 Mac。 而蓝牙权限属于 App，同一个程序在 root 下会被系统报 unauthorized。 这两个约束把管线切成了两半：

非特权（有无线电，无密钥）        特权（有密钥，无无线电）
rssi-scan        读手机的信标  ──→  presence-verify   验 HMAC，判真伪
state-advertise  广播 Mac 状态 ←──  permit-bridge     判近/远，写 permit
                                    （每窗口算好两个状态的标签递出来）

交接是一个文件（root 追加、App tail），不是第二条 FIFO——这条管线在 FIFO 开启顺序上死锁过。

3.2 特权那半边不从用户可写目录执行

早期版本把两个 root 程序拷进 App 数据目录再执行，而那个目录用户可写。 任何以你身份运行的进程都能替换它们，然后在下次开启监测时拿到 root—— 而你会看到一个写着「Outsie」的密码框，安心授权。 那等于把授权弹窗变成了洗白通道。 现在特权脚本随 bundle 发布，运行时不产生任何可执行文件，并且拒绝以 root 执行 $HOME 下的东西。

3.3 授权弹窗必须写 Outsie

macOS 把弹窗归给发起请求的可执行文件。借道 /usr/bin/osascript 就写 "osascript"—— 一个用户从没安装过的名字，出现在这个产品里唯一要他输管理员密码的时刻。 现在由 App 自己在进程内发起（在自己的线程上，因为那条命令要跑满整个监测周期）。

权限是每部手机各自的。「这部能解锁、那部只能锁屏」是合理要求，一个全局开关满足不了。

3.3屏幕上永远只有一个编号。 这六位是整个配对里唯一需要人核对的东西，所以这一屏不放任何别的号码、任何别的按钮。 曾经紧接着弹出一串八位十六进制「配对编号」，而没有任何东西说明该核对哪一个—— 在一个防中间人的流程里，那正是攻击者需要的困惑。

窗口是空闲超时，不是倒计时。它曾经是"按下开始配对后三分钟"， 而这三分钟里你要走到 Mac、点配对、等扫描、比对数字、点确认、输密码——很容易超时。 于是手机的窗口在交换进行到一半时关掉，Mac 配好了、手机没有。 现在每一个协议步骤都把截止时间往后推：人是这条流程里最慢的一步，不该是超时的那一个。

⚙︎ 挑选与排序

不平铺，是因为目录会长。一次实测里 Mac 送来 87 个操作。 平铺出来是一面按钮墙，而且找一个操作要先在心里按 App 把它们分一遍—— 目录本来就是按 App 组织的，屏幕照着它分组就行。

1.1标签既是分组，也是目标——这一点要说出来。 选中「终端」再点「左右分屏」，读起来像是把键发给终端， 而它确实就是：Mac 收到指令后先 activate 那个 App 把它切到最前面，再按键（console.rs 的 run_action）。 切到前面这件事会真的发生在屏幕上，所以屏幕上要先说， 不能让人按完才发现工作区被换掉了。

但「已按下」仍然不能写，「已发出」才能。 指令走的是单向信标，没有回程：切不切得过去、键落没落下， 手机一概不知道——Mac 那边找不到这个 App、屏幕锁着、 或者中途有人点走了别的窗口，都会失败而手机上看起来一样。 要写「已按下」，得让 Mac 在状态信标里回一个「最近执行到 seq=N」， 那是 macstate-v3。 未实现

标签条只列还有可见操作的 App。一个 App 的操作被全部藏起来，它的标签也一并消失—— 否则点进去是一片空白，而空白解释不了自己。

6.4一个操作都还没同步过来时，这一屏不是一排灰按钮， 而是先说这些按钮是什么、从哪来，再给「同步一下」。

「挑选与排序」放在这一屏底部，跟着它作用的东西走，不去设置页。

恢复成 Mac 上的顺序

这和「手机上没有编辑器」不冲突，两句话管的是两件事：

  • Mac 拥有"存在什么"——哪个 App、按哪几个键、每个操作对应哪个 cmd 字节。 留在 Mac 上有两个各自成立的理由：按键录制要一把真键盘； 而字节是协议的一部分，由 Mac 分配、写进 work-console-v1.json、此后不再变。
  • 手机拥有"显示什么、什么顺序"——从同步来的目录里挑出自己常用的， 藏掉不用的，拖动排序。挑选和排序是手指擅长的事，也是每部手机各不相同的事。

2.1这条需求完全不碰安全模型。 偏好不回传 Mac、不改目录、不改任何 cmd 字节、不参与签名。 目录仍然是 K_cat 签过的那一份，手机只是选择性地渲染它的一个子集。 少显示几个按钮，一个字节都没变。

隐藏一个操作不等于禁止它。被藏起来的操作，它的字节照样能发出去—— 换一部手机、重装一次 App，它就又在了。真正的权限开关在 Mac 上： 每部手机一个「让它按快捷键」，关掉之后 Mac 拒收这部手机的所有快捷键指令。 界面上必须把这句写出来，否则藏起来会被当成关掉。 Mac 上那个开关本身也还没做

同步之后新出现的操作：默认显示，排在末尾

反过来会很糟：用户在 Mac 上加好一个操作、在手机上点「同步一下」、然后找不到它—— 他会以为同步失败，而屏幕上没有任何东西能纠正他。 默认显示的代价只是多一个他可以马上藏掉的按钮， 默认隐藏的代价是一次看起来像故障的成功。

Mac 上删掉的操作：偏好按字节存，不按序号

偏好里存的是 cmd 字节（以及一个字节的排列），不是目录里的第几个。 序号会因为 Mac 上删掉一个操作而整体挪位，那样"藏起来的第 3 个"会变成另一个操作—— 和 §9 里指令字节不用序号是同一个理由。

渲染时，目录里没有的字节直接忽略。而且要在同步成功之后把它们从偏好里删掉， 不是留着：被释放的字节要等其它 240 个都用完才会复用，一旦复用， 留下的旧记录会让一个全新的操作一出生就是隐藏的。

偏好存哪：和目录分开的一份本地存储

手机本地 SharedPreferences，另起一份，不写进目录那一份。 目录是收到的事实，每次同步整份覆写；偏好是这部手机的选择，同步不该碰它。 混在一起，下一次同步就会把用户的排序连同目录一起冲掉—— 而那看起来会像"排序没保存住"，一个很难被报告清楚的 bug。

多台 Mac：一台一份，不共用

建议每台 Mac 各一份目录、各一份显示偏好。 两台 Mac 的操作根本不是同一批东西，而且 cmd 字节由每台 Mac 各自分配—— 共用一份偏好，会让"在 A 上藏起来的 17 号"在 B 上藏掉一个毫不相干的操作。 存储键用目录验签时匹配上的那个 keyId（配对 v3 之后每台 Mac 在手机上占一个槽）。

今天做不到，欠的是同一笔账。目录本身不带 Mac 身份， 验签时逐把钥匙试过去、只回答"验过了"，把"是哪一把"丢掉了； 手机上因此只存得下一份目录。和 §6.1「状态信标不带 Mac 身份」是同一个洞。 在补上之前，显示偏好只能是"这部手机的一份"。 未实现

App 的顺序还缺一个稳定标识：目录里的 App 今天只有名字。 Mac 的配置里已经有 bundleId，随目录发出来即可（加一个字段，旧解析器会忽略它，不动协议）。 在那之前 App 的顺序只能按名字存，Mac 上改个名等于回到默认——可以接受，要写在这里。

编辑态的形状

同一份内容换一种排布：网格变成行，因为一个拖动把手加一个开关需要一整行的宽度。 两段，App 在上、当前 App 的操作在下，都能拖。 编辑态里不执行任何操作——拖到哪都不会有一个字节发出去。

「恢复成 Mac 上的顺序」是必须有的：一个能把自己清空的偏好。 没有它，藏错之后用户唯一的出路是记得自己藏过什么。

07

关键流程

7.1 安装

三条会改变用户决定的事实在折叠线上面：它动哪里（在锁屏授权里加一条规则）、 怎么还原（先备份，移除时照备份还原并把结果读回来给你看）、 它挡不住什么（判断的是手机在不在，不是是不是你）。其余收进「更详细的」。

然后一次管理员密码。要点之前先说会看到什么：弹窗标题写 Outsie，不是的话就别输。

7.2 配对

手机「开始配对」  →  Mac「配对手机」  →  两边各出现六位数字
                                            ↓
                        两边都点「一样」（顺序不限）
                                            ↓
                   Mac 写入密钥（一次管理员密码）
                                            ↓
                   Mac「还差手机上那一下」 ← 等着听见手机用新钥匙签名
                                            ↓
                              配对完成

7.3 解锁

手机在附近 → 桥每 5 秒写一次 permit（root 拥有、带时间戳）→ 你在锁屏按回车 → 插件看到新鲜的 permit → 返回 Allow。

permit 15 秒过期，桥每 5 秒续一次。所以"在场"是一件要持续主张的事，不是一个开关： 桥崩了、手机走了、机器睡了，permit 自己就过期，门自动关上。

7.4 手机丢了

列表页上一张卡，不是藏在某处的设置——人最慌的时候会来找它。 第一句是你在眼前这台 Mac 上马上能做的：停用它的钥匙，立刻生效，不需要碰到手机。

远程停用还没做，所以每一台配过它的 Mac 都要各做一次。 直说，不给含糊的安慰。

09

协议规格

9.1 在场信标 repose-presence-v2（手机 → Mac，不可连接）

服务 UUID  0xFFF0
载荷       version(1) ‖ keyId(1) ‖ cmd(1) ‖ seq(4 BE) ‖ tag(8)        15 字节
预映像     "repose-presence-v2 beacon" ‖ keyId(1) ‖ counter(8 BE) ‖ cmd(1) ‖ seq(4 BE)
tag        HMAC-SHA256(K, msg)[0..8)
counter    floor(unix / 30)，从不传输——两端各自用自己的时钟推算，±1 窗口容差
cmd        0 无指令 · 1 锁屏 · 2 保留（曾用于"允许解锁"，已撤回）
seq        手机持久化递增；Mac 记住每个 keyId 的最大值，只接受严格更大的

指令放在信标里而不是新开连接：这样"必须在附近"是免费得到的—— Mac 得听得到这条广播才拿得到指令，而听得到的距离就是距离。没有第二个距离检查要维护，也就不会写错。

9.2 Mac 状态信标 repose-macstate-v1（Mac → 手机）

服务 UUID  0xFFF7
载荷       version(1) ‖ keyId(1) ‖ state(1) ‖ tag(8)                  13 字节
预映像     "repose-macstate-v1 beacon" ‖ keyId(1) ‖ counter(8 BE) ‖ state(1)

标签串和在场信标不同，这是承重的：一条"这台 Mac 开着"的录音，不能同时当成"手机在场"的伪造。

载荷经 local name 以十六进制携带——CoreBluetooth 在 macOS 上不允许外围发布 Service Data。 同样的字节，同样被标签覆盖。

9.3 配对 repose-pair-v2

服务 UUID  0xFFF1（连接式，只在配对窗口内广播）
M1  Mac → 手机   PK_M (65, SEC1 未压缩)              写 FFF2
P1  手机 → Mac   PK_P (65) ‖ Cp (32)                 读 FFF3
M2  Mac → 手机   Nm (16)                             写 FFF4
P2  手机 → Mac   Np (16)                             读 FFF5
名   双向        显示名（装饰性，不在记录里）          读写 FFF6

Cp   = SHA256("repose-pair-v2 commit" ‖ PK_M ‖ PK_P ‖ Np)     先承诺后公布
记录 = SHA256("repose-pair-v2 sas"    ‖ PK_M ‖ PK_P ‖ Nm ‖ Np)
数字 = 记录前 4 字节 mod 1e6，补零到六位
K    = HKDF-SHA256(ECDH_x, salt=记录, info="repose-pair-v2 presence-key")

先承诺后公布是整个协议的支点：手机必须在看到 Mac 的 nonce 之前就锁定自己的。 校验失败意味着有人在看到对方之后才选自己的数——那正是中间人会留下的痕迹， 所以那一刻的文案是"已中止，不要重试这次会话"，不是"出错了，再试一次"。

记录当 HKDF 的 salt：即便六位数字碰撞，中间人两边握着的也是不同的 K。

10

验收标准

  1. 干净安装到能解锁：从没装过开始，全程只用界面，走到锁屏按回车进入。不碰命令行。
  2. 拒绝路径：手机拿走 / 关掉信标 / 停掉监测，锁屏必须要求密码。三种都要单独验。
  3. 冒充：另一台设备广播同样的服务 UUID，必须 0 次放行。
  4. 移除即还原：移除之后 system.login.screensaver 与安装前逐字节一致。
  5. 每一句状态文案都指得出它读的是哪个事实。指不出来的删掉。
  6. 任何一屏上，必定失败的按钮不存在。
  7. 每一屏都能找到「密码一直都能登录」。
  8. 同步不冲掉选择：在 Mac 上新加一个操作再同步，它必须出现在手机上（排在末尾）， 而用户此前的排序和隐藏一条都不变。在 Mac 上删一个操作再同步，其余操作的顺序也不变。
11

开放问题

  • 中继攻击没有对策，也不打算有——那需要测距（UWB）或往返时延测量，蓝牙 RSSI 做不到。 界面上直说。
  • 手机能不能真的"按回车"：走蓝牙 HID 键盘理论上可行（HID 是驱动层，和合成事件不是一回事）， 但决定成败的那一环——锁屏时一台断开的 BR/EDR 键盘能否重连并被接受——零证据。 验证顺序是先买一把普通蓝牙键盘把 Mac 侧验完，零代码；那一步不过，后面全不用做。
  • 距离阈值还是占位值，需要真实校准，而且校准要能失败并要求重做。
  • 另一个第三方插件已经在这台 Mac 的锁屏规则里，k-of-n=1 下两者的相互影响没单独测过。
  • 字号与对比度：全局 52% 的字号声明小于 11px，--muted 对比度 3.11:1 不足。 数值与建议值记在 docs/design/ui-conventions.md §7，等一次专门的视觉评审。
