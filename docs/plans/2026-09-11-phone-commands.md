# 手机指令通道：锁屏按钮，以及「解锁」按钮到底能做什么

2026-09-11

## 起因

手机上没有任何主动控制 Mac 的能力。信标是**单向、不可连接**的广播——手机只发，
收不到回音，Mac 从不回话。这是当初的设计选择（省电、不给路人可连接的表面），
代价是手机上一个按钮都按不了。

用户要求加按钮，并接受为此新增通道。

## 先说清楚：「解锁」按钮做不到什么

**手机无法让 Mac 的锁屏打开。**

`system.login.screensaver` 这条授权规则是被**登录尝试**触发的：有人在锁屏上按了
回车，SecurityAgent 才会去调用我们的插件。没有登录尝试，插件根本不运行。外部进程
也无法替人提交那次尝试——锁屏下的合成事件注入被系统挡掉，root 也不例外。

所以「解锁」按钮的真实能力是**授权下一次回车**，不是代替你按回车。这一点必须写在
按钮旁边。一个叫「解锁 Mac」但按了之后 Mac 纹丝不动的按钮，是这个项目已经犯过
六次的同一类错误：界面宣称代码没做的事。

唯一能让手机真正按下回车的路子是让手机作为 **BLE HID 键盘**，与 Mac 做系统级蓝牙
配对。那是另一个量级的工程，本期不做，记录在此以免以后当作没想过。

### 于是「解锁」按钮被重新定位

把它从"更方便"改成"**更严格**"：

- **默认（今天的行为）**：手机在附近 → Mac 自动放行 → 你按回车就进。
- **开启「需要手机确认」后**：手机在附近**也不放行**，必须你在手机上点一下
  「确认放行」，Mac 才接受接下来的回车。

这才是一个真正增加了东西的按钮。它把"人在附近"这个可以被中继攻击伪造的事实，
换成"人**主动做了一个动作**"。

## 通道设计：不新开连接，扩展已认证的信标

拒绝的方案：让手机在按下按钮时广播一个可连接的服务、由 Mac 连上来取指令。
那等于把"不可连接"这个安全属性按需打开，多一个连接状态机、多一批出错路径，
而且按下按钮到 Mac 连上有秒级延迟。

采用的方案：**指令直接放进信标载荷，由同一把密钥的 HMAC 覆盖。**

理由：
- 认证已经在那儿了。指令和在场性用同一把密钥、同一个 tag，不需要第二套信任。
- Mac 的扫描器本来就在读每一条广播，不需要新进程、新连接、新权限。
- 「必须在附近」是**免费**得到的：Mac 必须**听得到**这条广播才能拿到指令，
  而听得到的距离就是蓝牙的距离。不需要额外写一个距离检查，也就不会写错。
- 信标不可连接这一条保持不变。

### 载荷

```
旧  ver(1) ‖ keyId(1) ‖ tag(8)                        = 10 字节
新  ver(1) ‖ keyId(1) ‖ cmd(1) ‖ seq(4 BE) ‖ tag(8)   = 15 字节
```

广播预算：UUID 列表 AD(4) + 服务数据 AD(4 + 15) = 23 / 31 字节。放得下。

```
msg = "repose-presence-v2 beacon" ‖ keyId(1) ‖ counter(8 BE) ‖ cmd(1) ‖ seq(4 BE)
tag = HMAC-SHA256(K, msg)[0..8)
```

标签串从 v1 改成 v2 是故意的：报文格式变了，旧串会让新旧两端在某些字段上
"验得过"，那种半兼容比干脆验不过更难查。两端必须同版本发布。

`cmd`：`0` 无指令（平时）、`1` 锁屏、`2` 确认放行。

### 防重放

`counter` 已经把指令限制在 ±1 个 30 秒窗口内，但窗口内仍可重放。所以：

- `seq` 由手机持久化保存，每发一条指令加一。
- Mac 记录每个 keyId 见过的最大 `seq`，只接受**严格更大**的。
- 手机发出指令后广播约 6 秒，然后 `cmd` 归零。

重放一条「锁屏」无害；重放一条「确认放行」不行——那正是 `seq` 要挡的。

## Mac 侧谁来执行

沿用现有的三段式，不新增进程：

```
rssi-scan   →  [root: presence-verify  |  permit-bridge.sh]
（读广播）      （持密钥、验 tag）        （决定近/远、写 permit）
```

- `rssi-scan`：CSV 增加 `cmd,seq` 两列。它仍然不做任何判断。
- `presence-verify`：把 `cmd`/`seq` 纳入 HMAC 校验，维护 seq 高水位，
  只把**验过且不是重放**的指令传下去。
- `permit-bridge.sh`：
  - `cmd=1` → 执行锁屏。
  - `cmd=2` → 立刻写 permit（严格模式下这是唯一的写 permit 路径）。

锁屏动作要以**控制台用户**身份执行（bridge 跑在 root 下），
用 `launchctl asuser $(stat -f %u /dev/console)`。

## 验证

- 单元：`seq` 高水位逻辑（新的、相等的、更小的、回绕）；tag 覆盖 cmd 和 seq
  ——改一个字节 tag 就该失效。
- 实机：手机点锁屏 → Mac 在几秒内锁上；重放同一条广播 → 第二次被拒。
- 回归：`cmd=0` 的普通信标行为不变，现有的在场判定不受影响。

## 不做

- 远程（非蓝牙距离）解锁。
- BLE HID 键盘。
- Mac → 手机的回执。手机按了按钮之后不知道 Mac 有没有照做——界面必须这么说，
  不能画一个"已锁定"的对勾。
