# 手机怎么按到 Mac 的键

2026-09-12 · 设计稿，**还没实现**

Mac 侧已经能按了（`src-tauri/src/console.rs` + `native/work_console.m`，见
`3c590d4`）。差的是手机上那一排按钮。

## 一个不明显的问题：目录在哪一端

先说一个让人意外的结论：**发指令很便宜，发目录很贵。**

在场信标里已经有一个 `cmd` 字节，经过 K 认证、带单调序号防重放，而且**已经实测跑通
过**（`presence-verify: command 1 seq=20 accepted from keyId=1`，手机上的「锁定 Mac」
就是它）。再加 240 个 cmd 取值，让每个快捷操作占一个，不需要任何新协议、不需要在
手机上开一个可连接的 GATT 服务、不多一寸攻击面。

问题不在发指令，在于**手机不知道该显示什么按钮**。操作的名字、图标、属于哪个 App，
全都在 Mac 上的 `work-console-v1.json` 里。一个字节装不下「左右分屏 ◫ 终端」。

所以需要一次连接——但只需要传目录，不需要传每一次按键。

## 形状

```
① 手机想控制 → 信标里发 cmd=3（请求目录）      认证、防重放，已有
② Mac 看到 → 作为 central 连上手机的 GATT      和配对同一个形状
③ Mac 写入目录（用 K_s 加密）                  一次，几百字节
④ 断开
⑤ 手机显示按钮；点一下 → 信标里发 cmd=16+i     每次按键，一个字节
```

**②③ 沿用配对已有的结构**：手机当 peripheral（`PairingServer.kt` 的写法），
Mac 当 central（`pair-with-phone.swift` 的写法）。两边都已经有能跑的代码可以照着写。

会话密钥：

```
K_s = HKDF(K, salt = 会话随机数, info = "repose-console-v1")
```

会话随机数由 Mac 在 ② 里给出，**每次重新协商**——目录不是秘密，但它泄露你在用哪些
App 和哪些快捷键，没有理由让它以明文在空中反复出现。

## 为什么不把每次按键也走 GATT

原计划是「Mac 连上手机，开一条会话，按键走会话」。改成按键走信标，理由：

- 信标那条路**已经通过实测**，会话那条还没有
- 每次按键都要建连接意味着延迟从「几秒」变成「连接协商 + 几秒」
- 手机上常开一个可连接的 GATT 服务，是这个产品目前唯一不存在的一类攻击面；
  只在传目录的那几秒开着，代价小得多

**代价**：一个字节只能表达「按第 i 个」，没有参数、没有返回值。手机点下去之后，
它知道自己发出去了，不知道 Mac 按没按成。这正是今天「锁定 Mac」的处境。

**要诚实地显示这一点**：按钮的反馈只能是「已发出」，不能是「已按下」。
（`ui-conventions` 1.1 —— 手机主屏那句「已发出」就是为这个写的。）

要真正的回执，得让 Mac 在状态信标里回一个「最近执行到 seq=N」。那是 macstate-v3，
不在这一轮。

## 手机侧

`ControlScreen.kt`：App 切换条 + 按钮网格，从电脑卡片的「控制」进入。
四种情形按 hi-fi 稿：可用 / 不在附近 / Mac 上关着 / 缺辅助功能权限
——**后两种按钮仍然在，点下去说去哪儿开**，而不是消失。

**手机上没有编辑器**：在手机上配电脑快捷键，是把最难的输入放在最小的屏幕上。
目录只能读，改要去 Mac。

## 还需要先决定的

1. **cmd 取值怎么分配**。16+i 的 i 是目录里的序号，那么改一次配置，序号就变了——
   手机上还没刷新目录时按下去，会按到别的操作上。**这是会真的按错键的路径。**
   倾向：目录带一个 revision（`work-console-v1.json` 里已经有 `revision` 字段），
   cmd 的高位带上 revision 的低 2 位，对不上就拒绝执行并让手机重新取目录。
2. **谁触发 ③**。Mac 要一直在扫 cmd=3，还是只在快捷控制页打开时？
   一直扫更好用，但也意味着 Mac 会因为一个信标就主动去连手机。
3. **每部手机的「允许控制」开关存哪**。计划里说在手机控制页，每部手机一个。
   那需要先有 P3 的「每部手机一个 keyId」，否则一台 Mac 上分不出是哪部手机在发。
   **这条把 P4 的开关挂在了 P3 上。**

## 已经能做、不依赖上面任何一条的

Mac 侧的操作编辑器。现在 `work-console-v1.json` 只能手改，而
「能按的操作」那一页是只读的。加编辑器不碰协议、不碰密钥、在一台机器上就能验完。
如果要挑下一件事做，是这件。

# 实现进度与一个没绕过去的障碍（2026-09-12 05:50）

## 已经做完并实测的：指令那一半

见 `a4d93d0`。手机发 `cmd=16`，Mac 收到、验证、映射到「左右分屏」、尝试执行、
诚实地因为缺辅助功能权限而拒绝并记录。**没有新协议、没有新连接。**

上面「三个还没决定的问题」里的第一条**解决了，而且比原方案好**：

> 指令字节编的是目录里的序号，改一次配置序号就变，手机没刷新会按错操作。

不是「把 revision 编进字节」，而是**字节本身就是一个稳定标识符**：由 Mac 分配、
存进 `work-console-v1.json`、此后不再变。删掉一个操作不会让其它操作改号；被释放的
字节要等到其它 240 个都用完才会复用，所以一部睡了很久的手机**按下去什么都不发生**，
而不是按到那个顶替了它的操作上。

## 障碍：目录必须能验真，而验真要用 K，可 App 读不到 K

一开始以为目录只要"传过去"就行。不是。

**一份伪造的目录可以给按钮贴错标签。** 按钮上写「锁屏」，发出去的字节在 Mac 自己的
配置里对应的却是别的操作——你按的和它做的不是一回事。所以目录必须带上这台 Mac 的签名。

签名要用 K。而 K 在 `/var/db/repose-unlock/presence-key.N`，**root:wheel 0600，
App 读不到**——这是特意的（`presence-privileged.sh` 整个存在的理由就是把 root 那半边
的表面积压到最小）。

绕不过去的几条路：
- 让特权半边签 → 要给 root 链条加一个请求/响应通道，正是那个文件在避免的东西
- 目录不验真、让人在 Mac 上确认 → 把安全责任推给每次取目录的人
- 手机不验，只显示 → 回到「按钮可以说谎」

## 解法：配对时派生第二把钥匙

```
K        = HKDF(ecdhX, salt = transcript, info = "repose-pair-v3 presence-key")   ← root 独占
K_cat    = HKDF(ecdhX, salt = transcript, info = "repose-pair-v3 console-key")    ← App 可读
```

同一次 SAS、同一个 transcript，**不同的 info 标签，所以是两把互不相关的钥匙**。

- `K_cat` 只能签目录，签不出在场信标——标签分域保证了这一点
- 它放在 Mac 的用户态（app_data_dir 下 0600），泄露它的人能伪造一份目录，
  **但开不了这台 Mac 的锁**
- 手机那边一样存进 keystore，只用来验签

这是唯一一条既不给 root 加通道、又不让按钮可以说谎的路。

## 还剩的实现

1. 两端各多派生一把 `K_cat`（配对时，各两行）
2. 手机开一个 console GATT 服务（`FFF9`），**只在请求目录的那几十秒内可连接**——
   和配对时那套「临时变成可连接」完全一样的做法
3. Mac 作为 central 连上去，写入 `目录 ‖ HMAC(K_cat, 目录)`；目录超过 MTU 要分片
4. `ControlScreen.kt`：App 切换条 + 按钮网格，四种情形（可用 / 不在附近 /
   Mac 上关着 / 缺辅助功能权限）——**后两种按钮仍然在，点下去说去哪儿开**

第 2、3 条是一条新的 BLE 传输。**2026-09-12 凌晨没有动它**：那个时候开始写一条新的
传输层，写出来的错误会长得像功能。

# 做完了（2026-09-12 06:15）

见 `afc187e`。实测链路：配对（六位数字 484280）→ 手机点「向 Mac 要一份」→
Mac 送来 87 个操作 → 手机验签通过、画出按钮（tmux / 左右分屏 / ⌃b %）→
点「按一下」→ Mac 上：

```
cmd=16 「左右分屏」没按成：macOS 还没允许 Outsie 替你按键。
```

**除了最后那一下按键（缺辅助功能权限，那是用户自己要给的），每一环都是真的。**

上面「还需要先决定的」三条：

1. **cmd 取值怎么分配** —— 解决了，而且比原方案好：字节由 Mac 分配并存进配置，
   是稳定标识符而不是序号。
2. **谁触发目录发送** —— Mac 的指令监听器一直在跑（它本来就要监听按键指令），
   收到 `cmd=3` 就发。手机那边的接收窗口只在用户点「要一份」之后开 60 秒。
3. **每部手机的「允许控制」开关** —— **还没做**。P3 已经给了每部手机自己的 keyId，
   所以现在分得出是哪部手机在发，这条不再被阻塞。

## 还剩的

- **每部手机一个「允许控制」开关**（Mac 上的手机控制页）
- **手机重新配对后不会丢掉旧钥匙**，于是会广播一个没有任何 Mac 持有的槽位。
  无害（`auth=NOKEY`），但占一路广播。Mac 那边会删掉旧槽位，手机无从得知。
- **回执**：手机只能说「已发出」。要说「已按下」，得让 Mac 在状态信标里回一个
  「最近执行到 seq=N」——那是 macstate-v3。
