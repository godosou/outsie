本文合并 trust-first / minimal-friction / failure-first 三份草案，并逐条处理了三份批评。凡是与三份原稿冲突的地方，以本文为准。

## 0. 主干选择与嫁接清单

### 0.1 主干：failure-first（设计 3）

理由三条，按分量：

1. **它是唯一一份产出了可机械检查的设计约束的稿子。** §2 的七个出路原语加上那句「任何新失败态如果找不到归属，说明我们还没想清楚，不能发布」，直接对应类型层的一个 `Remediation` 枚举——可以写成测试，可以在 code review 里执行。另外两份的失败处理是逐屏写的文案，落到代码里没有共同形状。
2. **它是唯一一份把项目自己的教训做成了状态机约束的稿子。** 「四项健康检查里三项静态可查，唯独『macOS 会不会加载这个组件』查不出来」→ 所以真实锁屏是进入就绪态的唯一路径。这个项目已经付过两次学费（200+ 测试全绿而真实解锁零次；验收绿过一次、复现三次全败）。把验收标准搬进产品，是本功能最值钱的一条结构性决定。
3. **它在可恢复性上得分最高**，而这个功能的真实卖点不是「少输一次密码」，是「你随时能把系统拿回来」。

- **设计 3 的「每天第一次解锁仍输密码，默认开」** → 默认关，且只在实验 E5（锁屏提示文字）通过后才提供这个开关。理由见 §5.9。
- **设计 3 的「蓝牙关闭且 Mac 锁屏时发手机通知」** → 手机蓝牙关着时手机无法知道那台 Mac 锁着，触发条件不可判定，改成本地可判定的条件。
- **iPhone 出现在任何界面示意、文案或官网里** → 首发只承诺 Android（见 §9.1）。

## 1. 命名与三句话

**功能名：手机钥匙。** 开关标题：**回车解锁**。全产品一次都不出现「自动解锁」「无感解锁」「秒开」。

三句话在设置页、安装流程、成功页、托盘、README、website 中**逐字一致**，不改写、不缩写、不换说法：

> **① 手机在身边时，回车就是你的密码。**
> **② 它不会在你走近时自己打开。密码框还是会出现，你不用输任何字符，直接按一下回车。**
> **③ 密码始终照常可用。**

第一句给价值，第二句给预期，第三句给安全感。凡是第一次向用户介绍这个功能的地方，①② 必须同屏；凡是失败态，③ 必须出现。

第四句只在安装前和第一次失败时出现，不进常驻文案：

> **④ 偶尔手机还没被认出来，回车会失败一次。再按一次通常就好了。**

语域：全程使用设置页已有的「安全 / 系统」档——严肃、具体、主动交代限度。**这个功能里禁用嘴欠语域**，唯一允许的温柔是演练成功页的一句「退路是通的」。

## 2. 这份设计依赖的事实，和三个还没做的实验

### 2.1 已经有证据的（`docs/validation/2026-09-09-a1-plugin-load.md`）

- ad-hoc 签名的第三方 Authorization Plugin 在 macOS 14.6.1 + SIP 开启下能被加载并听从。
- 授权求值只在**提交一次解锁尝试**时发生。锁屏时不运行，密码框出现时也不运行（等 15 秒零日志）。
- 安全语义实测过 **2×2 四格**（密码：错误 / 空 × 手机：在 / 不在）。**「正确密码」那两格没有测过**——设计 1 §4.1 说「四格里测过三格」是错的，真值表是 2×3，没测的是两格。产品真正依赖的是「手机不在场 + 正确密码 → 进得去」，实验室里没有证据。这就是演练 A 存在的工程理由。

### 2.2 三份草案都搞错的一件事：安装器生成的形态没有被验证过

`authdb-edit add-subrule` 做的是 **prepend 并保留原有条目**，`tests/authdb_edit_test.sh:62` 断言结果是 `${SUB},use-login-window-ui`。而 A1 验证通过的规则是 `[ai.repose.spike, authenticate-session-owner-or-admin]`——那是**手工换过**的形态。

**也就是说：安装器现在会生成的形态从没被验证能加载插件；被验证的形态安装器不会生成。**

三份草案都把这件事画进了「我们会改动这台 Mac 的什么」那一屏，并各自基于它写了最贵的一块文案（设计 1 §5.1 为它付出了全稿唯一一次主动的转化牺牲）。这个前提必须先由实验回答。

一条重要的旁证：**这台开发机此刻的真实规则是**

```
[com.openai.sky.CUAService.AuthorizationPlugin.remote, use-login-window-ui]   k-of-n = 1
```

而 `install.sh:32-34` 的注释说这个第三方插件是「observed working on a real Mac」。如果 `[ours, use-login-window-ui]` 也能触发插件链，那么：

- 不需要动 `use-login-window-ui`；
- **锁屏界面不会换绘制方，整块「锁屏会看起来不一样」的披露不存在**；
- **不会引入 `authenticate-session-owner-or-admin` 的语义变化**（「谁的密码能解这台机器的锁屏」不变）。

### 2.3 发布前必须做完的七个实验

界面按实验结果分支，不预设答案。**E1 / E3 / E6 是 A3 的前置，没结果不许写对应文案。**

| # | 问题 | 怎么测 | 决定什么 |
|---|---|---|---|
| **E1** | `[ours, use-login-window-ui]` k-of-n=1 能不能触发插件链？ | 在 VM 上跑一次 `install.sh`（stock 规则），锁屏提交一次 | 决定走**形态 A**（无视觉变化、无语义变化）还是**形态 B**（必须换 `-or-admin`，两块披露都要写）。约一小时 |
| **E2** | 若必须走形态 B：`authenticate-session-owner-or-admin` 是否让本机任意管理员账户都能解你的锁屏？ | 建第二个管理员账号，锁屏，输它的密码 | 决定形态 B 下管理员授权前那一屏要不要写「你的锁屏从只认你变成认你或任何管理员」 |
| **E3** | 规则在、bundle 不在（用户把 App 拖进废纸篓、升级中途）时会怎样？ | 装好后移走 bundle，锁屏提交空密码；命令行 `security authorize` 做焦点无关的复现 | **已测，结论相反且更糟**：不是「密码失效」，而是**锁屏 fail-open，空密码即可绕过**。见 [../validation/2026-09-09-e3-fail-open.md](../validation/2026-09-09-e3-fail-open.md)。**这是发布阻塞**：当前 `k-of-n=1` 形态不能进产品 |
| **E4** | 只改 `system.login.screensaver` 时，重启后的登录窗口（`system.login.console`）是否完全不受影响？ | 装好后重启，用密码登录 | 通过的话，「重启一定能进」是全设计最硬、最便宜的一条兜底。三份草案都没写 |
| **E5** | `LoginwindowText` 在插件生效后的锁屏界面上还显不显示？ | 一条 root `defaults write`，与安装共用同一次授权 | 决定「按一下回车」这句提示能不能出现在它唯一有用的那一刻。也决定 §5.9 那个开关要不要做 |
| **E6** | mechanism 超时压到 250ms、由守护进程从缓存立即应答，端到端是否稳定？ | 改 `PERMIT_TIMEOUT_MS`，接 IPC 后跑验收 | 决定「手机不在时每次密码解锁要不要先卡一下」。见 §2.4 |
| **E7** | `,privileged` 变体为什么不被调用？ | 见 `docs/plans/2026-09-09-permit-design.md` | 决定 `peer_identity.rs` 的对端签名 pin 怎么写 |
| **E8** | 换规则形态能否关掉 fail-open？ | 逐一换形态、移走 bundle、CLI authorize，再到真实锁屏验证 | **已答，但要看锁屏而非 CLI**：CLI 上「机制 + 后接 builtin 密码机制」像是 fail-closed；**真实锁屏相反**（[E11](../validation/2026-09-09-e11-lockscreen-grant-model.md)）——机制 `Allow` 直接解锁、`Deny` 硬失败且不退到密码机制。**没有既免密又缺失即 fail-closed 的规则形态**。仍成立：fail-open 是 evaluate-mechanisms 缺失机制的通性 |
| **E9** | bundle 在位但**签名失效/无法加载**（比删除更贴近升级现实）时是什么行为？ | 破坏签名或替换成坏二进制，跑 `fail_open_probe.sh` | 决定健康检查是查「bundle 存在」还是必须查「`codesign -v` 通过」 |
| ~~**E10**~~ | ~~机制向 context 注入凭据让 builtin:authenticate 静默通过~~ | — | **已收回**（[E11](../validation/2026-09-09-e11-lockscreen-grant-model.md)）：锁屏上手机在场时机制 `Allow` 本身就解锁，`builtin:authenticate` 不运行，没有可注入的对象，注入正确/错误凭据结果相同。前提不成立 |
| **E12** | 健康检查守护：开机 + `WatchPaths` + 慢定时断言「规则引用的 bundle 存在且 `codesign` 通过」，悬空即从 authdb 移除子规则 | **已实现并真机验证**（[记录](../validation/2026-09-09-e12-healthcheck.md)）：真实 install.sh 装好守护，`rm` bundle 后**约 4 秒**规则自动退回纯密码，`security authorize` 从 YES 翻成 NO；uninstall 全清不锁死 | **G2 的解法**。E8/E11 证明 fail-open 无法靠规则结构关闭，只能预防悬空引用 + 运行期修复 |

### 2.4 关于那 1.5 秒：改掉它，不是写它

三份草案都漏了 `plugin.c:39` 的 `PERMIT_TIMEOUT_MS 1500`，注释自己写着这是「用户在密码框出现前盯着冻结屏幕的时间」。手机不在场的每一次密码解锁都要先付这 1.5 秒。

**本设计的答复是改掉它，不是给它写文案。** 依据是 `docs/plans/2026-09-09-permit-design.md` 已确定的方向：插件不再读文件，而是向 root 守护进程发一次 IPC。守护进程持有 BLE 的滚动在场缓存，**它不需要现场扫描就能回答**。因此：

- **R-P1**：mechanism 侧超时 **250ms**；守护进程必须从缓存立即应答。
- **R-P2**：连不上 socket、超时、应答不可解析 → **立即 Deny**（fail-closed）。守护进程挂掉之后，机器应该更难进而不是更容易进。
- **R-P3**：守护进程在收到 `screenIsLocked` 时立即拉起持续扫描并保持缓存热（`macos.m:44-67` 已有这个信号）。这同时压低了「唤醒后第一次回车正好撞上扫描窗口冷启动」的失败率。

**若 E6 显示停顿仍然可感知**，则必须在安装前那一屏加一句，措辞已备好：

> 手机不在身边时，密码框会比现在晚零点几秒出现——那是它在确认你的手机确实不在。确认不到，它就把你交还给密码。

## 3. 状态机

### 3.1 三个动作，三种代价（这是状态划分的骨架）

| 动作 | 位置 | 系统改动 | 配对 | 恢复成本 |
|---|---|---|---|---|
| **暂停**（关开关 / 托盘暂停一小时） | 面板顶部 Toggle、托盘 | 保留 | 保留 | 点一下 |
| **撤销设备** | 设备行内 | 保留 | 删除 | 重新配对 |
| **移除并还原** | 面板底部 outline 按钮，永远可见 | 全部还原 | 删除 | 重新安装 |

旧模型只有「卸载」，结果是用户为了临时关掉一个功能而卸载它，然后再也不装回来。

| 任意 | **bundle 缺失但规则仍在（悬空引用）** | S7-危险 | **安全紧急态**：锁屏此刻 fail-open，空密码可绕过（[E3 记录](../validation/2026-09-09-e3-fail-open.md)）。健康检查一旦发现，必须立即从 authdb 移除子规则、恢复到纯密码，并上红色横幅。这是唯一「组件不一致」比「组件全无」更危险的情形 |
| 任意 | 撤销设备 | S3 | 组件留着，只清密钥 |
| 任意 | 移除并还原 | S0 | 还原报告 |

### 3.4 不变量（每条都要能在界面上被验证）

1. **任何状态下，密码都能进，且插件失灵时必须 fail-closed（要求密码），绝不 fail-open（免密放行）。** E3 实测出当前 `k-of-n=1` 形态在 bundle 缺失时是 fail-open 的——空密码即可绕过锁屏（[记录](../validation/2026-09-09-e3-fail-open.md)）。E8/E11 进一步证明**没有既免密又缺失即 fail-closed 的规则形态**，所以这条不变量不能靠规则结构达成，只能靠**预防悬空引用 + 运行期修复**（健康检查，见 E12）。今天**不成立**，是发布阻塞（门禁 G2）。界面在每个失败态里主动申明密码可用，不等用户问。
2. **只有 S6a 是绿点。** S6b「手机不在」是中性灰，不是黄色警告——这是这个功能每天要经历几十次的正常状态。
3. **每个非就绪状态有且只有一个主按钮**，按钮名是动词。
4. **全局横幅只为「按回车真的会失败且需要你动手」出现**，不为「手机不在」出现，也不为「没开」出现。这是对现有 `.security-alert` 用法的刻意偏离：闲置锁屏是安全功能，没开就该被念叨；手机钥匙是便利功能，没开不该。
5. **任何撤销 / 移除操作都不需要手机在场。**
6. **失败时不自动关开关。**（偏离 `idle-lock-failed` 的先例，理由：手机不在每天都会发生，自动关意味着用户每天早上要重开一次。只有组件从系统里消失才降级到 S0。）
7. **就绪态不上概览页。** 一个安全功能每天向你汇报「我今天也很正常」，是在为将来真正需要注意的那天贬值。

### 4.2 F22 的分流表——这是本设计最核心的一块

用户看到的现象完全一样（按回车没进去），原因有四种，**下一步完全相反**：「组件根本没被加载」要重装，「慢了一拍」只要再按一次回车。给一句笼统的「解锁失败」，用户要么无谓重装，要么在真坏了的时候一直白按。

**判定依据不能是插件日志。** A1 记过：插件日志属主 `_securityagent`、权限 0600，`admin` 读不了——那次「0 行」藏住的是一个成功。设计 3 的原方案（读插件日志）实现出来会重演这个坑。

**证据通道必须是守护进程**。它是 IPC 的应答方，天然知道「这次求值发生过、我答了什么」。

| 守护进程记录 | 真实原因 | 事后卡片第一句 | 出路 |
|---|---|---|---|
| 本次锁屏周期内**从未被问到** | 插件没被加载（F1/F6），或规则没生效（F2） | 「刚才 macOS 没有调用解锁组件」 | R1 / R2 |
| 被问到，答 Deny，且手机长时间不在场 | F9 / F12 / F13 | 「刚才没有看到你的手机」 | R5 |
| 被问到，答 Deny，但手机最近可见 | F14 慢一拍 / F19 判定偏远 | 「刚才手机还没被认出来」 | 再按一次；连续 3 次 → R4 |
| 答 Allow 但屏幕仍锁着 | 罕见，链路后段异常 | 「组件放行了，但系统没有解锁」 | R1 + 复制诊断 |

**已知限制（必须写进实现说明）**：「插件加载了但连不上 socket」与「插件根本没加载」在守护进程侧看起来一样，都归入第一行。这不影响出路——两者的下一步都是 R1。

### 4.3 出路收敛：七个原语 + R0

| 原语 | 按钮文案 | 管理员密码 | 覆盖 |
|---|---|---|---|
| **R1 重新安装组件** | 「重新安装组件」 | 是 | F1、F5、F6、F22-a、F22-d |
| **R2 修复规则** | 「修复规则」 | 是 | F2 |
| **R3 重新配对** | 「重新配对」 | 否 | F16、F17 |
| **R4 重做校准** | 「重做校准」 | 否 | F18、F19、F20 |
| **R5 去手机上处理** | 「怎么打开」/「在手机上打开」 | 否 | F9、F12、F13 |
| **R6 撤销这台设备** | 「撤销这台设备」 | 否 | F15、F16、F21 |
| **R7 移除并还原** | 「移除手机钥匙并还原系统设置」 | 是 | F3、F5、F7，以及用户随时想退出 |
| **R0 可以先不管** | **无按钮，一句话** | — | F5、F8、F13 |

**R0 值得单独说**：有些失败的正确下一步就是什么都不做，但必须明确说出来。一个半装完的状态放着不管是安全的（**前提：E3 通过**）；如果界面只是红着不说话，用户会自己去命令行乱删——删掉备份，然后卸载就只剩不可逆的路径了。**给出路不等于给按钮。**

**约束（可在 code review 里执行）**：任何新失败态如果找不到归属的原语，说明还没想清楚，不许发布。

### 4.4 呈现强度只有三档

| 档位 | 用在哪 | 何时 |
|---|---|---|
| **全局横幅**（复用 `.security-alert`） | 所有页面顶部 | 只在「按回车真的会失败」时：F1、F2、F5、F6、F17、F24；F13 超过 24 小时 |
| **面板内状态条** | 设置页手机钥匙面板顶部 | 所有异常，包括日常的 F9/F13 |
| **事后解释卡** | 解锁后主窗口前台，一次，不重复 | 最近一次锁屏尝试失败且原因可判定 |

### 4.5 打扰预算

- **一次性预算（安装期间）：不设上限。** 用户主动走进来，有明确起点终点，随时可退出，退出时系统零改动。所有沉重的内容压在这里。
- **常驻预算（装完之后）：只保留全局横幅一条主动通道**，且只在上表那几种情况出现。
- **Mac 侧一条系统通知都不发。** Mac 的通知渠道属于休息提醒，那是这个 App 的本职。手机钥匙不许去抢那个注意力预算。需要在锁屏时说的话，全部走手机端本地通知——Mac 那时候锁着，用户也看不到。

| 手机 App 被系统停掉后重新启动 | **Outsie · 手机钥匙已恢复**　刚才手机上的 Outsie 被系统停过一次。想避免再发生，把 Outsie 设为不受限制。`[怎么设置]` |
| Mac 侧发生撤销 | **Outsie · MacBook Pro 已撤销这台手机**　这台 Mac 现在只接受密码。 |

（设计 3 原方案的第一条触发条件是「蓝牙关闭**且这台 Mac 处于锁屏**」——手机蓝牙关着时无法知道 Mac 的状态，唯一的通道就是断掉的那条。已改。）

## 6. 对后端的要求（A3 的直接输入）

### 6.1 错误怎么表达

现有三种方式（静默 `return` / `-> bool` / 无 payload 事件）都装不下这份设计。**新建一层：**

```rust
#[derive(Serialize)]
#[serde(rename_all = "camelCase")]
pub struct UnlockError {
    pub code: UnlockErrorCode,          // 机器可判定，前端用来选文案
    pub detail: String,                 // 系统返回的原话，用于「复制诊断信息」
    pub remediation: Option<Remediation>,
    pub evidence: Option<Evidence>,     // 期望值 / 实际值对照，用于修复页的 diff
}

#[derive(Serialize)]
#[serde(rename_all = "kebab-case")]
pub enum UnlockErrorCode {
    PreflightRuleShape,     // F3
    AuthorizationDenied,    // F4
    InstallFailed,          // F1 写入失败
    HalfInstalled,          // F5 / F9 半状态
    ComponentNotLoaded,     // F1
    RuleTampered,           // F2
    BackupMissing,          // F7
    PairingExpired, PairingMismatch,
    CalibrationOverlap,     // F18
    KeyMismatch,            // F17
    BluetoothOff, BluetoothUnauthorized, PhoneAppStopped, PhoneUnseen,
    DaemonUnavailable,
    DrillNotObserved,       // 演练超时：不等于失败
    Unsupported,            // !window.repose / 非 macOS
}

#[derive(Serialize)]
#[serde(rename_all = "kebab-case")]
pub enum Remediation {          // §4.3 的七个原语 + R0，一一对应
    ReinstallComponent,         // R1
    RepairRule,                 // R2
    RePair,                     // R3
    ReCalibrate,                // R4
    FixOnPhone { hint: PhoneHint },   // R5
    RevokeDevice,               // R6
    UninstallAndRestore,        // R7
    LeaveItAlone,               // R0：前端渲染成一句话，不渲染按钮
}

#[derive(Serialize)]
pub struct Evidence { pub expected: String, pub actual: String, pub read_at: String }
```

**约束**：`Remediation` 是封闭枚举。新增失败态如果找不到归属的变体，说明还没想清楚，不许发布。前端对每个变体各有一个按钮文案，一一对应，没有第八个按钮。

### 6.2 命令清单

全部返回 `Result<T, UnlockError>`。参数一律走单个 `value` 对象，沿用现有惯例。

| command | 参数 | 返回 | 说明 |
|---|---|---|---|
| `unlock_get_snapshot` | — | `UnlockSnapshot` | **每次调用都重新读**：authorizationdb、bundle 存在与 cdhash、socket 权限位、守护进程状态、传输状态。带 `readAt` |

| `unlock_install` | `{ variant }` | `UnlockSnapshot` | 一次管理员授权内完成：备份 → 装 bundle → 落 `uninstall.sh` + `RESTORE.txt` → 写 right（**plist 里必须带 `comment`**，见下）→ prepend 子规则 → 重读校验 |
| `unlock_repair` | `{ target: Rule \| Component \| Daemon }` | `UnlockSnapshot` | R1 / R2。修复规则时**只加回我们那一条，不动任何别的条目** |
| `unlock_uninstall` | — | `UninstallReport` | 见下 |
| `unlock_pair_begin` | — | `PairingSession { code, qrPayload, expiresAt }` | 3 分钟 |
| `unlock_pair_cancel` | — | `()` | |
| `unlock_calibrate_sample` | `{ kind: Near \| Far }` | `CalibrationReport { separable, marginDb, samples }` | `Near` 在配对成功时由后端自动调用一次 |
| `unlock_revoke_device` | `{ deviceId }` | `UnlockSnapshot` | **不要求手机在场** |

**`unlock_install` 的三条硬要求**（都在同一次管理员授权内完成，不额外弹窗）：

1. `ai.repose.unlock` 这条 right 的 plist 必须写 `comment` 键：
   `Installed by Outsie (repose.app). To remove: sudo /var/db/repose-unlock/uninstall.sh`
   Apple 自己就这么用（stock screensaver 规则的 comment 就是这么写的）。任何未来打开 `security authorizationdb read` 的人——包括三年后的你——第一眼就知道这是谁干的、怎么撤。
2. `uninstall.sh` 与 `RESTORE.txt` 落到 `/var/db/repose-unlock/`，与备份同目录。**删掉 App 不影响它们。**
3. `RESTORE.txt` 里必须包含这台机器安装前的规则全文，以及形态 A/B 的 stock 常量。

**`UninstallReport`**：

```ts
{
  readAt: string
  ruleNow: string          // 卸载后重新读到的规则全文
  backupUsed: boolean
  diffAgainstBackup: string[]   // 空数组 = 逐字一致
  rightRemoved: boolean
  bundleRemoved: boolean
  keysRemoved: boolean
  residual: string[]       // 明确列出没有还原的东西（F7 路径）
}
```

前端**只渲染这些字段**，不允许出现「已还原」这类断言性文案而没有对应读数。

### 6.3 快照结构

```ts
type UnlockSnapshot = {
  readAt: string                 // ISO8601，界面必须显示
  state: 'not-installed' | 'installing' | 'half-installed' | 'awaiting-password-drill'
       | 'awaiting-pairing' | 'awaiting-calibration' | 'awaiting-verification'
       | 'ready' | 'needs-repair' | 'paused' | 'uninstalling'
  presence: 'near' | 'away' | 'transport-unavailable'   // 轴 C，永不上横幅
  variant: 'A' | 'B' | null      // 安装用的是哪种规则形态
  components: Array<{
    id: 'rule' | 'component' | 'daemon' | 'transport'
    health: 'ok' | 'degraded' | 'broken' | 'unknown'
    detail: string
    evidence?: Evidence
    remediation?: Remediation
  }>
  componentInvocation:           // 只能来自守护进程的实际观测
    | { kind: 'observed'; at: string }
    | { kind: 'never-observed' }   // 前端必须渲染成「还没有观察到被调用」，不许显示绿点
  device: { id, name, platform, pairedAt, lastSeenMs } | null
  stats: { unlocksToday: number; lastUnlockAt: string | null }
  lastFailure: {                 // 驱动 §5.14 事后解释卡
    at: string
    cause: 'not-invoked' | 'phone-absent' | 'phone-slow' | 'allowed-but-locked'
    shown: boolean
  } | null
  macosBuild: string             // 变化时把 state 降级回 awaiting-verification
  componentVersion: string
}
```

| 事件名 | payload | 频率 | 驱动 |

| `repose-unlock-snapshot` | `UnlockSnapshot` | 低（状态变化时） | 面板 + 全局横幅 |
| `repose-unlock-presence` | `{ presence, lastSeenMs }` | 高（秒级） | 只驱动面板状态行，**绝不驱动横幅** |

### 6.5 守护进程与插件侧的要求（来自批评，非可选）

| # | 要求 |
|---|---|
| **R-P1** | mechanism 超时 **250ms**（不是 1500ms）；守护进程从滚动在场缓存立即应答 |
| **R-P2** | 连不上 socket / 超时 / 应答不可解析 → **立即 Deny**（fail-closed）。守护进程挂掉之后机器应该更难进 |
| **R-P3** | 收到 `screenIsLocked`（`macos.m:44-67` 已注册）时立即拉起持续扫描并保持缓存热 |
| **R-P4** | permit **必须换成 IPC**，不再是 `/tmp` 文件。发布门禁，见 §8 |
| **R-P5** | consume socket `0600`（或 `0660` 配受限组），**绝不 world-writable**；安装后由健康检查断言权限位，不能只靠 plist 写对 |
| **R-P6** | 守护进程负责写 F22 的证据：每次锁屏周期记录「是否被问到 / 答了什么 / 何时」，以 `root:wheel 0644` 暴露只读状态文件。**不要读插件日志**——它是 `_securityagent` 0600，`admin` 读不了，A1 记过这个坑 |
| **R-P7** | 配对密钥、校准参数、安装时的 macOS build 与 cdhash **一律不进 localStorage**，需要 Rust 侧新建持久层（Keychain / root-only 目录） |

## 7. 前端实现约束

1. **全部装进现有的 `Modal` 组件**（`App.tsx:64-86`，自实现焦点陷阱 + Esc），安装流程在同一个 Modal 内换 step。**不新建窗口**——label 不匹配 `main` / `break-*` 就没有任何权限。
2. **不引入 stepper 或进度条。** 三屏、六十秒、不可回退的流程，进度指示只是在提醒用户「还有几步没走完」。让每个按钮说出下一件事就够了。安装期间的五行打勾进度是**动作日志**，不是进度条——它的价值在于「哪一步失败了」，而不是「走到几分之几」。
3. **CSS 写在新文件 `src/phone-key.css`，用 `activity-chart.css` 的多行格式**，不要延续 `styles.css` 的超长单行。
4. **深色模式必须逐条补 `[data-theme=dark]` 覆盖。** token 不是全量的（大量硬编码十六进制），新增的状态点、徽章、`.fallback-pledge`、`.change-manifest` 三类组件只用 `:root` 变量的话深色下会缺一半。
5. **不引入 destructive red。** 应用里唯一的红是拉伸示意点 `#c74943`。「撤销设备」「移除并还原」用既有的暖棕警告色系（`#f7efe2` / `#ecdfc8` / `#aa8b58`）+ outline 加重边框。移除不是危险行为，是安全出口。
6. **`!window.repose` 降级**：整个面板渲染为只读介绍态 + 「桌面版专属」徽章，Toggle 灰态不可点。否则主页演示会崩（AGENTS.md 要求区分「浏览器模拟」与「安装包里的原生功能」）。
7. **`break.html` 不做任何手机钥匙相关展示。** 全屏休息是这个 App 唯一真正强制的界面，不许被别的功能占用。
8. **上线时必须同步**：README 里「手机钥匙与手机工作台不包含在此安装包中」这一行必须改；`website/` 中英文版本、下载、功能与演示同步。中英文基准句是 §1 的 ①②③。

## 9. 这份设计还没解决的问题

### 9.1 iOS —— 首发不支持，且不确定能不能支持

**需要的信息**：iOS 应用进后台后，manufacturer data 与 local name 都不进广播包，只剩 overflow area 的 service UUID，承载不了旋转的签名身份。而约束 5 要求判定不能依赖建立 GATT 连接（发现 1.9s + 连接读 1.5s 已超预算）。

**已知资产**：`tools/ble-spike/android` 只有 Android，实测设备是 realme RMX3888。

**结论**：**首发只承诺 Android。** 任何界面、文案、官网、示意图里一次都不出现 iPhone。要支持 iOS，需要先做一个实验回答「后台 iOS 能不能在 overflow area 里放一个够用的可轮换标识」，或者接受「iOS 走 GATT 连接 + 更长的预算 + 更长的第一次回车等待」。**在那个实验有结果之前，不许在任何地方暗示支持 iPhone。**

### 9.2 锁屏那一刻我们说不了话

约束 3 的提示在它唯一有用的时刻（用户盯着密码框）无处显示——机制在提交之前根本不运行。

**唯一可能的通道是 `LoginwindowText`**（一条 root `defaults write`，**与安装共用同一次授权**，设计 2 否掉它的理由「要再要一次授权」是错的）。但它在 SecurityAgent 绘制的锁屏上还显不显示，未知。

**需要**：实验 E5。通过则作为一个可选开关提供（默认关，文案：「在锁屏上写一行提示：按回车即可进入」）；不通过则这个缺口只能靠演练 B 建立的肌肉记忆来补。**§5.9 那个「每天第一次仍输密码」的开关直接依赖 E5**，E5 不通过就不做。

### 9.3 中继攻击

技术上今天挡不住。可能的方向（都需要单独调研）：距离测量（AoA / CS，硬件依赖）、时序上界、要求手机侧一次不打扰的挑战应答（预算不够）。

**当前处置**：写进 §5.3 的「它挡不住什么」，作为**决策依据**（「这些情况下建议你别开」）而不是免责声明；并在托盘提供一键暂停，让安全的选择比不安全的选择更省事。

### 9.4 手机被拿走且解锁时仍能进

技术上堵不上（没有 3 秒预算做二次确认）。「每天第一次仍输密码」能把它从「永久免密」限制成「一天之内免密」，但它依赖 E5（否则每天制造一次无解释失败）。

**需要**：E5 的结果。

### 9.5 校准阈值的默认值

出厂默认阈值从哪里来？现在没有数据。**需要**：在若干台不同机型 / 机箱 / 桌面布局上采一组「近 / 远」样本，得到一个保守的初值和一个可用的 margin 判定门限。在有数据之前，「用保守的默认值」这条出路（宁可多输一次密码，也不在你不在时放行）没有具体数字。

### 9.6 多台 Mac 的撤销

配对是每台 Mac 独立的。§5.13 承诺「列出本地已知的其余 Mac」——**这个「本地已知」的来源没有定义**。手机侧知道它配过哪些 Mac，但 Mac 侧不知道。

**需要**：确定手机是否在配对时把「你还配着哪些 Mac」同步给 Mac（涉及一个跨设备状态同步通道，目前不存在），或者把这句话改成「如果你在别的 Mac 上也配过这台手机，需要打开那台 Mac 分别撤销」——不列名单。**倾向后者**，因为它不需要新通道，且不会显示一份可能过时的名单。

### 9.7 `,privileged` 变体

为什么不被调用，未知。它决定 `peer_identity.rs` 的对端签名 pin 怎么写（非特权变体跑在 `_securityagent` uid=92，不是 `authorizationhost`），而两条路的安全性质不同，值得单独决策而不是顺手选一个。**需要**：实验 E7。

### 9.8 「唤醒 Mac 的那次按键会不会落进密码框」

A1 第 119-121 行记过这个坑，验收脚本用了 24 次退格。手机在场时无所谓（错误密码也放行），**手机不在场时它会变成一次失败的密码尝试**。§5.3 的 01 写着「不输任何字符」，这句在真机上是否成立，值得在写进 README 之前单测一次。

**需要**：一次十分钟的手工验证。若不成立，01 的措辞要改成「唤醒之后，如果框里有东西，清掉再按回车」——那会让整个流程的说服力下降一档，所以必须先测。

### 9.9 卸载后 UI 的一件小事

形态 B + 备份丢失 + 规则里有别人的条目时，锁屏界面永久停在新样子（§5.12）。这是唯一一个「移除之后回不去」的场景。目前的处置是**如实说**。

**可能的改进**：安装时就把 stock 常量写进 `RESTORE.txt`，用户可以手工恢复。已列入 §6.2 的安装第 3 条要求，但「用户会不会真的去做」不在我们控制内。
