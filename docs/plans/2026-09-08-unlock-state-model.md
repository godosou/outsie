# 解锁功能的状态模型（A2 设计输入）

日期：2026-09-08

分支：`feat/phone-unlock-walking-skeleton`

这份文档只处理 A2 中**不依赖 A1 结论**的那一半：用户会处在哪些状态、每个状态的出路是
什么。依赖 A1 的那一半（安装到底要用户做哪几步）单列在最后，等实测结果填。

## 从旧模型继承什么

`codex/phone-proximity-unlock` 的 `src-tauri/src/unlock.rs` 里那套 snapshot 结构是这个
分支里少数值得保留的设计。

**保留：**

| 结构 | 为什么值得留 |
|---|---|
| `ComponentHealthSnapshot { policy, plugin, service, transport }` | 四个组件的拆分与真实安装一一对应，排障时能直接指出哪一环断了 |
| `CalibrationPhase` 含 `OverlapRejected` | 把「远近两组样本分布重叠过多」这个真实失败编码进了类型，而不是笼统的 failed |
| `PairingSession { expires_at_epoch_ms }` | 配对会话必须过期，这一点在类型里就强制了 |
| `limitations: Vec<UnlockLimitation>` | 主动把残余风险（中继攻击、手机被盗、强行停止）呈现给用户，而不是藏起来 |
| `PairedDevice { platform }` | 多设备、跨平台从一开始就在模型里 |

**必须拆掉：**

| 结构 | 问题 |
|---|---|
| `AuthorizationGate { evidence_record: String, install_allowed }` | `evidence_record` 是一个指向 `docs/validation/...` 的仓库内路径。**产品的数据模型不该引用开发期的验证文档。** 用户拿到的构建里出现这个字段没有任何意义 |
| `UnlockCapability::GateClosed` | 把「我们还没验证完」这个开发状态做成了产品状态 |
| `UnlockLimitation::Task8GateClosed` | 同上，而且直接写了内部任务编号 |
| `ComponentHealth::NotChecked` | 用户视角下「没检查」不是一个状态，只是还没查。查一下就有答案了 |

这三个字段是「把开发期的门禁思维焊进产品」的具体证据 —— 也解释了为什么那套 UI 只能
对着一个永远失败的后端设计。

## 一个改变产品定义的发现：唤醒是承诺的一部分

查证 Apple 的 authd 行为后确认：**macOS 在机器锁着不动的时候并不评估
`system.login.screensaver`**。授权求值（以及插件的 `MechanismInvoke`）只在用户真的
尝试解锁时才开始 —— 按键、动鼠标、唤醒显示器。

所以「人走近，Mac 自己就亮起来并解锁，全程不碰机器」在这条技术路线上做不到。
实际能做到的是：

> 你走近，唤醒 Mac（按一下键 / 开盖），它**不问密码**直接进去。

这跟 Apple Watch 解锁 Mac 是同一个模式，也是这类产品的行业标准形态。**手机替你省掉的是
输密码，不是唤醒。** 界面文案必须照这个说，不能承诺"完全无感"，否则第一次使用就会被
认为是坏的。

这个发现同时是测试设计的前提：验收测试里如果没有唤醒动作，机制根本不会运行、测试必然
超时 —— 而那个超时看起来和「macOS 拒绝加载插件」一模一样。

## 修订后的状态模型

### 顶层：用户处在哪一步

```
未安装 ──安装──▶ 已安装未配对 ──配对──▶ 已配对未校准 ──校准──▶ 就绪
   ▲                   │                    │                 │
   └────────卸载────────┴────────────────────┴─────────────────┘
                        
   任一状态都可能横向掉进：组件异常（可修复） 或 已撤销（需重新配对）
```

关键：**这是一条线性的引导路径，但每一步都可能横向掉出去。** 旧 UI 的问题是它只画了
线性路径，没画掉出去之后怎么回来。

### 每个状态必须回答的三个问题

任何一个状态，界面上都要能回答：

1. **现在是什么情况**（一句话，不是错误码）
2. **为什么**（如果是异常）
3. **下一步点哪里**（必须有一个具体动作，「联系支持」不算）

`ComponentHealth::Degraded` 是反例：它说了「有问题」，没说是什么问题，也没说怎么办。
修订为每个组件携带一个可选的 `remediation`：

```
ComponentState {
    health: Ready | Missing | Broken | Unavailable,
    detail: String,          // 「插件已安装但系统未加载」
    remediation: Option<Remediation>,   // Reinstall | Repair | Reboot | ReadOnly
}
```

### 失败态清单（每条都要有出路）

| 失败 | 用户看到 | 出路 |
|---|---|---|
| 插件文件在但系统没加载 | 「系统没有加载解锁组件」 | 重新安装 |
| 授权规则被其他软件改掉 | 「解锁配置被修改」 | 修复配置（只动我们自己那条） |
| 手机蓝牙关闭 | 「找不到已配对的手机」 | 提示开蓝牙；同时说明密码始终可用 |
| 手机被强行停止 | 「手机上的 Repose 已被系统停止」 | 引导去手机上重新打开 + 加白名单 |
| 手机丢失/被盗 | —— | **撤销该设备**，且必须能在手机不在场时完成 |
| 校准样本重叠 | 「远近距离区分不出来」 | 重做校准，并提示换个位置 |
| 密钥状态损坏 | 「需要重新配对」 | 撤销旧配对 + 重新配对 |

**贯穿所有失败态的一条**：系统密码始终可用，且界面要主动这么说。用户对自动解锁最大的
恐惧是「它坏了我是不是就进不去了」。

### 残余风险要主动呈现

从旧模型继承 `limitations`，但改成用户能懂的话，并且只在相关时显示：

- 中继攻击：攻击者可以转发手机的无线信号，让 Mac 误以为你在附近
- 手机被盗且处于解锁状态时，靠近 Mac 仍会解锁
- 高风险环境建议关闭此功能

这三条不是免责声明，是**设计约束**：它们决定了这个功能不该在什么场景下被推荐使用。

## 依赖 A1 的部分（待填）

安装引导的具体形态完全由 A1 的实测结果决定：

| A1 结果 | 引导形态 | 可行性 |
|---|---|---|
| ad-hoc + SIP 开启即可加载 | 一次管理员授权，体验接近普通 App | 好 |
| 需要关闭 library validation | 多一步系统级配置，需要解释清楚风险 | 可接受 |
| 必须 `csrutil disable` | 用户要重启进恢复模式关掉系统完整性保护 | **需要重新评估这个功能值不值得做** |

第三种情况下，让用户为了一个便利功能永久关闭 SIP，代价远大于收益。届时应该考虑放弃
Authorization Plugin 路线，或者把功能降级为「靠近时不自动解锁，但把密码框准备好」。

**在拿到 A1 结果之前不画安装引导的界面。**
