# E3：规则在、bundle 不在时，正确密码还能不能进 —— 已解决（结论相反且更糟）

日期：2026-09-09

> **已解决 → 见 [2026-09-09-e3-fail-open.md](2026-09-09-e3-fail-open.md)。**
> 后来用命令行（不抢焦点）+ 一次锁屏级 GUI A/B 对照定死了结论：不是「进不去」，
> 而是 **bundle 缺失时锁屏 fail-open，空密码即可绕过**。本文以下是当时「未定」阶段的
> 原始记录，保留以存证推理过程；真正的结论以 fail-open 那篇为准。

状态（历史）：**未定（inconclusive）**。不是通过，也不是失败。

## 为什么这是发布门禁

设计里贯穿始终的一句承诺是「系统密码始终照常可用」。如果用户把 Outsie 拖进废纸篓、
或者升级中途失败，authorizationdb 里的规则还指向一个已经不存在的 bundle —— 这时候
正确密码还能不能进，决定这句承诺有没有证据。不通过就必须把它改成条件句，
并且安装引导必须相应改写。

## 已经观测到的

受控条件下（单条命令内完成，中途未让出焦点）：

| 项 | 值 |
|---|---|
| bundle | 已移出 `/Library/Security/SecurityAgentPlugins/` |
| 规则 | `[ai.repose.spike, use-login-window-ui]`，仍指向缺失的 bundle |
| 输入送达 | **是**（客户机 HID 空闲 71s → 9s） |
| 提交内容 | `admin` + 回车 |
| 结果 | **保持锁定 16 秒** |
| 插件日志 | 0 行（bundle 不在，机制无法运行，符合预期） |

## 为什么不能据此判定失败

两条未排除：

1. **不确定 `admin` 是不是这台 VM 的真实密码。** 它来自 FIRST-BOOT.md 的建议值，
   但设置是人工完成的，可能设了别的。
2. **没有验证那串字符真的落进了密码框。** 输入送达客户机是确定的，但落点未验证 ——
   屏保关闭的时机、24 次退格是否清空、焦点是否在输入框上，都没有独立证据。

「结果符合某个假设」和「因为正确的原因符合」是两回事，这个项目已经为混淆这两者付过代价。

## 正确的做法

**由人手动完成，不要用自动化。**

1. ssh 进 VM：`sudo mv /Library/Security/SecurityAgentPlugins/ReposeSpike.bundle /tmp/away`
2. 确保 `/tmp/repose-permit` 不存在
3. 锁屏，在 VM 窗口里输入**你自己设的真实密码**
4. 能进 → E3 通过；进不去 → E3 失败，且是发布阻塞项

一秒钟的事，比按键注入可靠得多，也不需要抢占宿主机焦点。

## 顺带记录：GUI 自动化的代价

为完成这类实验所做的按键注入会**抢占宿主机焦点**，正在用电脑的人会被打断。
这不是可以忽略的副作用 —— 需要人在场的实验就交给人做，不要为了自动化而自动化。
