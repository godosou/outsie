# E13：在场判定没有密码学身份，任何人都能冒充这台手机

日期：2026-09-09

状态：**未修复。当前实现可被任何人在几十行代码内绕过。**

## 判定「是我的手机」的全部依据

`tools/ble-spike/mac/rssi-scan.swift`：

```swift
let serviceUUID = CBUUID(string: "7265706F-7365-0001-8000-00805F9B34FB")   // 第 15 行
let charUUID    = CBUUID(string: "7265706F-7365-0002-8000-00805F9B34FB")   // 第 16 行
```

判定链路是：按 service UUID 过滤扫描 → 连上去 → 读 characteristic → 拿到字符串
`repose-hello` → 认为「手机在场」。`permit-bridge.sh` 在此之上只做 RSSI 强弱与迟滞判断，
**没有任何身份输入**。

全链路 grep 不到 P-256 / ECDSA / signature / verify / Keystore —— 一处都没有。

## 因此

**攻击者只需要写一个广播同样 UUID、返回同样字符串的应用。** 这两个常量在本仓库里
明文出现（UUID 4 处、字符串 7 处），是公开信息。带着这样一台设备走到目标 Mac 旁边，
桥就会判定在场、写下 permit，此后**空密码回车即可进入**。

不需要接触目标 Mac，不需要知道任何密码，不需要目标手机在场。

## 已有的加固防的是另一件事

permit 本身已经做得相当扎实：root 属主、15 秒新鲜度、root-only 目录、`O_NOFOLLOW` +
`S_ISREG`（FIFO 会永久阻塞 root 机制）、以及守护进程的单次消费模式。

**但这些防的是「目标 Mac 上的本地攻击者」，防不了「冒充手机的远程攻击者」。**
本地攻击者写不了 permit；冒充者根本不需要写 permit —— 他让我们自己的桥去写。

把这两件事分清楚很重要，否则「permit 已加固」会被误读成「在场判定已安全」。

## 更严重的一层：界面已经向用户承诺了这把钥匙

手机端的 Phone Key 配对界面（`PairingScreen.kt`）当前显示：

> 确认这是同一台设备
> Mac 上现在应当显示下面这串。不一致就别继续。
> 配对码 **UMX5EW**
> Repose 不用蓝牙地址认设备——地址每几分钟自己变一次。**认的是配对时交换的那把钥匙。**
> 〔一致，完成配对〕

**这把钥匙不存在。** 源码自己说得很清楚，`PairingScreen.kt:15` 的注释：

> confirming just flips the local "paired" flag and drops the user onto the guarding home.

「完成配对」执行的全部动作是 `store.paired = true`（第 79 行）。配对码由
`AppStore.pairingCode` 在本机用一个字母表随机生成并存进 SharedPreferences，
**从未发送给 Mac、从未被比对、不参与任何判定** —— 所以「Mac 上现在应当显示下面这串」
这句话不成立，Mac 根本不知道这串码。设备列表同样是 `seedMacs()` 造的种子数据。

全仓库（`tools` / `native` / `src-tauri` / `src`）grep `P-256|ecdsa|KeyPairGenerator|SecKey|CryptoKit`
**零命中**。Phone Key UI 那次提交的 1199 行全部是界面代码。

这一层比「功能缺失」更需要认真对待：**界面向用户做出了实现并不支持的安全承诺**，
而且承诺的正是本文档指出缺失的那件事。这与旧分支 validation 文档「声称没装过任何东西、
实际装了」是同一类错误，区别在于这次是给用户看的。

在密钥交换真正实现之前，这段文案必须改成如实描述，或者这个界面不应出现在任何人手里。

## 为什么之前没暴露

到目前为止的每一次实测，手机都是**我们自己的**那台。实验设计从来没有引入过第二台设备，
所以「能认出这台手机」和「能认出任何广播这个 UUID 的设备」这两件事，
在所有已有证据里表现完全一致。

这也说明验证方案本身有个盲区：**所有测试都只证明了正向路径**
（真手机在 → 解锁；真手机走 → 锁上），没有一个测试问过「假手机在 → 会怎样」。

## 修复的前提约束（都是实测得来的）

| 约束 | 数值 | 对方案的影响 |
|---|---|---|
| 蓝牙地址不可用作身份 | 22 次广播重启 = 22 个不同 peripheral id；另有约 4.4 分钟一次自发 RPA 轮换 | 身份必须来自密码学，不能来自地址 |
| macOS 扫描窗口节流 | 约每 1500ms 一次（四次独立实验落在同一格点） | 发现本身就慢 |
| 发现延迟 | p50 1925ms / p95 5407ms | 三秒预算已经很紧 |
| 建连 + 读特征值 | 约 1–2 秒 | 「每次解锁做一次握手」很可能来不及 |
| 手机 Doze 存活 | **未测**（B4 未做） | 不能假设手机随时可被连上 |

## 验收判据

修复必须能通过一个**当前必然失败**的新测试：

> 用一台**未配对**的设备广播同样的 service UUID 并返回同样的载荷，
> 放在 Mac 旁边，锁屏后按回车 —— **必须仍然要求密码**。

没有这个测试，「防住了冒充」这句话就没有证据。当前实现跑这个测试会解锁。
