# E3 —— 结论：插件缺失时锁屏 **fail-open**（可被空密码绕过）

日期：2026-09-09

状态：**已确认（CONFIRMED）**，在真实锁屏路径上、A/B 对照、多次复现。

这一项原本是「插件没了，正确密码还能不能进」的发布门禁。实测把它整个反转了：
真正的风险不是「进不去」，而是 **谁都能进，不用密码**。

## 一句话

当 `system.login.screensaver` 的规则通过 `k-of-n=1` 引用我们的机制
（`ai.repose.spike`）、而该机制的 bundle **缺失**时，锁屏可以用**空密码**绕过。
macOS 的授权引擎在「引用的机制插件无法加载」时 **fail-open**：把无法实例化的
子规则当作「通过」，`k-of-n=1` 于是直接放行。

## 怎么测的：只改一个变量的 A/B

规则始终是 `["ai.repose.spike", "use-login-window-ui"]`，`k-of-n=1`，permit 始终不在，
提交的始终是**空密码**。唯一变化的是 bundle 在不在。测的是**真实锁屏界面**
（客户机被 ScreenSaverEngine 锁住，GUI 注入空密码 + 回车），不是命令行。

| 条件 | 机制是否运行 | 空密码 + 回车 | 锁屏结果 |
|---|---|---|---|
| bundle **在位** | 运行，`Deny`（插件日志 `uid=92 result=Deny`） | 提交 | **保持锁定** ✓ |
| bundle **移走** | 无法运行（插件日志空） | 提交 | **解锁** ✗ |

- 两组的输入都经 `vm-wake-submit.sh` 校验过确实送达客户机（HID 空闲下降）。
- bundle 在位那组的插件日志 `uid=92`（`_securityagent`）证明这是**真实 loginwindow 路径**，
  不是命令行产物。
- bundle 移走那组插件日志为空，证明放行**不是**机制批准的，是机制根本没运行。

结论：**移走 bundle 是把「保持锁定」翻转成「解锁」的唯一变量。**

## 命令行上更快地复现同一现象

`security authorize system.login.screensaver`（不带任何凭据）也表现出同一 fail-open，
而且不需要 GUI、不抢焦点，适合做回归探针：

| bundle | 调用者 | 给密码 | 结果 |
|---|---|---|---|
| 不在 | admin（会话所有者） | 无 | `YES (0)` —— 放行 |
| 不在 | root（非会话所有者） | 无 | `YES (0)` —— 放行 |
| 在 | admin | 无 | `NO (-60007)` —— 拒绝 |
| 在 | root | 无 | `NO (-60007)` —— 拒绝 |

admin 和 root 都放行，排除了「因为调用者是会话所有者才放行」的解释：**只跟 bundle
在不在有关**。命令行结论与锁屏结论一致，互为佐证。

## 为什么会这样

规则要求 `{ai.repose.spike, use-login-window-ui}` 里有 **1 个**通过。正常时：
手机在 → `ai.repose.spike` Allow → 满足，无需密码；手机不在 → `ai.repose.spike` Deny
→ 落到 `use-login-window-ui` → 要密码。设计本身是对的。

但当 bundle 缺失，`ai.repose.spike` 这个子规则**无法实例化**，授权引擎把它当作
**成功**而不是失败。`k-of-n=1` 只需要一个成功，于是这个「幽灵成功」直接满足了规则，
密码子规则**根本没被走到**。

## 危险窗口在哪

我们自己的安装/卸载脚本顺序是**安全**的：
- `install.sh`：先放 bundle（第 98–99 行），再写规则引用（第 163 行）。
- `uninstall.sh`：先移除规则引用（第 76 行），再删 bundle（第 96 行）。

也就是说，**只要走脚本**，规则永远不会引用一个缺失的 bundle。危险只出现在**绕过脚本**
让 bundle 消失、而规则还在的情况，而这些恰恰都是现实会发生的：

1. 用户把 App 直接拖进废纸篓（不知道有个系统级 bundle 和一条 authdb 规则）
2. 升级中途失败：旧 bundle 已删、新 bundle 没到位、规则一直在
3. 系统迁移 / 某些 MDM / OS 大版本升级清空 `SecurityAgentPlugins`
4. bundle 签名在未来某次 OS 更新后失效、无法加载（**未测**，见下）

任何一条发生，机器就从「锁着」变成「空密码可进」。

## 对架构的硬约束（发布阻塞级）

1. **不能依赖「运行后修复」。** 看门狗进程无法在锁屏时补救——机器一旦锁上，
   守护进程要么没机会跑、要么跑了也改不动正在被评估的规则。安全必须来自**结构**，
   不是**反应**。

2. **当前 `k-of-n=1` + 子规则的形状对「bundle 缺失」是 fail-open 的，不能进产品。**
   需要一个「机制不能明确 Allow 时就要求密码」的 **fail-closed** 规则结构。

3. **必须查清 fail-open 是 `k-of-n` 特有，还是 `evaluate-mechanisms` 缺失机制的通性。**
   如果是通性，那么任何引用我们机制的规则形状都挡不住「bundle 缺失」，唯一的安全来自
   **预防**——绝不让规则引用缺失的 bundle。这决定下一步（见待办 E8）。

4. **健康检查必须断言「规则引用的每个 bundle 都存在且可加载」**，并在检测到悬空引用时
   立刻把子规则从 authdb 移除（恢复到纯密码）。这是**预防**危险窗口，不是锁屏时补救。

5. **卸载引导必须显式警告**：不要手动把 App 拖进废纸篓，要走卸载流程；否则会留下悬空规则。
   （更强的做法：让 App 自身在退出/被删时无法留下悬空引用，但这在纯用户态很难保证。）

## 顺带修正历史结论

上次 GUI E3 观测到「bundle 移走后输入 `admin` 保持锁定 16 秒」，当时判为「未定」。
现在能调和：那次输入是否落进密码框从未验证，而 `admin` 大概率不是真实密码；
本次用**空密码**且验证了输入落地，结果是解锁。两者不矛盾——真正决定放行的是
bundle 缺失导致的 fail-open，与输进去的是什么无关。
