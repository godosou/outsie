# E11 —— 真实锁屏的授权模型：第一个机制说了算；命令行不是它的代理

日期：2026-09-09

状态：**已确认（CONFIRMED）**，真实锁屏（SecurityAgent）四次 GUI 实验，A/B 一致。

这一篇同时**收回** E10（凭据注入）和 E8 中「fail-closed 骨架存在」的结论——它们都建立在
`security authorize` 命令行的行为上，而命令行在这一点上与锁屏**相反**。

## 一句话

在真实锁屏上，`system.login.screensaver` 若是 `evaluate-mechanisms` 链
`[我们的机制, builtin:authenticate]`，**裁决完全由第一个机制决定**：

- 机制 `Allow` → **立即解锁**，后面的 `builtin:authenticate` 不被走到（密码对错、注入对错都无关）。
- 机制 `Deny` → **立即保持锁定、硬失败**，`builtin:authenticate` 不被走到（**输正确密码也进不去**）。

命令行 `security authorize` 恰好相反：机制 `Allow` 会**继续**到 `builtin:authenticate` 把关，
`Deny` 才停。所以**命令行不是锁屏的有效代理**，这一条是花了代价才认清的。

## 先厘清什么才算 bug

产品承诺是**「手机在场 → 免密解锁」**。所以**手机在场时，输错密码、甚至不输，照样解锁，
是功能本身，不是漏洞**——在场即免密，密码在此刻本就无关紧要。下表里 #1、#3 都属于「功能正常」。
真正该 fail 的只有两格：手机**不在**时能不能挡住（#2），以及手机不在时**正确密码能不能进**（#4）。

## 证据：四次锁屏 GUI 实验，只有真实锁屏路径

规则始终是 `evaluate-mechanisms`，permit=文件式在场信号。

| # | 机制 | permit（手机） | 输入 | 机制裁决 | 锁屏结果 | 判定 |
|---|---|---|---|---|---|---|
| 1 | credential | 在 | 正确密码 | Allow | 解锁 | ✓ 功能正常 |
| 3 | credential | 在 | **错误**密码 | Allow | 解锁 | ✓ 功能正常（在场即免密） |
| 2 | credential | **不在** | 空框 | Allow | 解锁 | ✗ **本应要密码** |
| 4 | permit | **不在** | **正确**密码 | Deny | 保持锁定 | ✗ **正确密码也进不去** |

- **#1 与 #3 结果相同（都解锁）**：说明手机在场时解锁来自机制 `Allow`，**与输入/注入无关**——
  这正是免密功能。也因此，**E10 想让「注入的凭据经 builtin:authenticate 静默通过」是无的放矢**：
  手机在场时机制 `Allow` 已经解锁，`builtin:authenticate` 根本不会运行，没有可注入的对象。
  **E10 收回。**
- **#2**：credential 模式在**手机不在**时也返回了 `Allow`（我原本的设计是「总是 Allow、只条件性注入」，
  误以为 builtin 会兜底）。锁屏上 `Allow` 直接解锁 → 手机不在也解锁。这是**我这个模式的设计缺陷**，
  修法是「手机不在时返回 `Deny`」（与 permit 模式一致）——不是锁屏本身的问题。
- **#4（决定架构的一格）**：permit 模式在手机不在时 `Deny`，链**硬失败**，`builtin:authenticate`
  不运行，**输入正确密码也无法解锁** → 链**不提供密码兜底**。→ **E8「机制 + 后接 builtin
  密码机制 = fail-closed 骨架」收回**，那是纯 CLI（机制 Allow 会继续、Deny 才停）得出的，锁屏相反。
- #2/#4 都在 `killall authd` 冲掉缓存后复现过，排除凭据缓存假象。

（说明：近几次日志出现 `uid=501` 而非早期的 `uid=92`，疑与 `killall authd` 后 SecurityAgent
上下文有关；不影响结论——四次的裁决都严格随第一个机制的 Allow/Deny 走。）

## 为什么 k-of-n 能提供密码兜底，而链不能

已在跑的、验收测试通过的形态是 **k-of-n=1** 的
`[ai.repose.spike, use-login-window-ui]`，其中 `ai.repose.spike` 是**独立子规则**
（evaluate-mechanisms，只含我们的机制）。密码兜底来自 **k-of-n 在子规则失败时去试下一条子规则**：

- permit 在 → 机制 Allow → 子规则 `ai.repose.spike` 成功 → k-of-n 满足 → 免密解锁。
- permit 不在 → 机制 Deny → 子规则失败 → k-of-n 去试 `use-login-window-ui`（class=user）→ 密码。

**兜底是「k-of-n 换下一条子规则」给的，不是「一条链里换下一个机制」给的。** 链里 Deny 是硬失败，
不会换机制。这就是 #4 保持锁定、而 k-of-n 形态下同样情形能出密码框的区别。

## 由此坐实的架构结论

把 E3 / E8 / E10 / E11 合起来，结论是硬的：

1. **免密解锁**要求我们的机制能**单独**让规则通过（k-of-n 子规则单独满足）。
2. 而「机制单独能通过」正是 **fail-open** 的根因：bundle 缺失时该子规则被当成功（E3、E8）。
3. **想用规则结构做到 fail-closed**（缺失即要密码）就不能让机制单独通过——那就没有免密。
4. **链这条替代路在真实锁屏不存在**：Deny 硬失败、无密码兜底（E11 #4）；Allow 又解锁一切（#2/#3）。

> **免密解锁 与「缺失即 fail-closed」用规则结构不可兼得。** 既然要免密（产品的核心价值），
> 就必须接受 fail-open 的结构，并用**预防**把它关死——这正是 E8 的第一条结论，现在被坐实为
> **唯一**的路，而不是可选项之一。

## 因此，发布门禁 G2 的解法（更新）

不是「换成 fail-closed 规则形态」（不存在），而是**预防悬空引用 + 运行期修复**：

1. **安装/卸载顺序**（已实现）：bundle 永远先于规则引用存在、后于规则引用消失。
2. **启动期 + 周期性健康检查**（待实现）：断言规则引用的每个 bundle 都存在且 `codesign -v` 通过；
   一旦发现悬空引用，**立即从 authdb 移除该子规则**，规则退回纯 `use-login-window-ui`（纯密码）。
3. **卸载引导显式警告**：不要手动拖废纸篓，要走卸载流程。
4. 健康检查无法在「机器已锁 + 引用已悬空」的瞬间补救，所以它的价值在于**关闭时间窗**
   （开机即查、后台常驻查），把「bundle 消失」到「健康检查修复」之间的窗口压到最小。

## 收回清单

- **E10**：凭据注入让 builtin:authenticate 静默通过 —— **假阳性，收回**（#1 vs #3）。
- **E8 的「fail-closed 骨架存在」** —— **收回**，锁屏上链无密码兜底（#4）。E8 关于
  「缺失机制被当作『该步通过』」的观察在命令行成立，但**不能外推到锁屏的授权裁决**。
- **命令行 `security authorize` 作为锁屏代理** —— 仅在 fail-open 判定上与锁屏一致（E3 已双向验证），
  在「机制 Allow/Deny 之后是否继续把关」上与锁屏**相反**，不可作代理。
